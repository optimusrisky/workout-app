# 技術スタック・認証方式

## インフラ・DB

| 項目           | 選定             | 理由                                                                                                   |
| -------------- | ---------------- | -------------------------------------------------------------------------------------------------------- |
| ホスティング   | Vercel           | Next.jsとの相性が良く、デプロイ・環境変数・HTTPSの運用がほぼ自動。バックエンド/インフラ初心者でも運用負荷が低い |
| DB             | Neon(マネージドPostgres) | 標準的なPostgresのため、将来AWSのRDS等へ移行する場合もデータ移行の難易度は低い(ベンダーロックインが小さい) |
| ORM            | Prisma           | マイグレーション管理(`schema.prisma`)が直感的。Prisma StudioでDBの中身をGUI確認できるため、DB初心者に向く |

### AWSについて(将来検討・今回スコープ外)

AWSを将来的に使いたい意向はあるが、今回は採用しない。

- 1ヶ月でR1をリリースする必要があり、AWSの学習(IAM/VPC/RDS等)とアプリ実装を同時に進めるとスケジュールが破綻するリスクが高い
- Neon(Postgres)は標準的なSQLなので、将来AWS RDSへ移行する際の技術的な障壁は低い
- 「AWSを学ぶ」はこのアプリのリリース後、独立したタスクとして扱う(例: R3以降でAIフィードバック生成部分だけLambdaに出す等)

## 認証

| 項目         | 選定                          | 理由 |
| ------------ | ----------------------------- | ---- |
| 認証方式     | Auth.js(NextAuth) + Prisma Adapter | 無料でベンダー依存がなく、将来ユーザーが増えても認証基盤のコストが発生しない。ユーザー情報を自前のPostgresに持てるため、ワークアウト記録等のドメインデータと同じDBで`userId`により素直に紐付けられる |
| ログイン手段 | Googleログインのみ(R1)         | パスワードのハッシュ化・リセットフロー等の実装・セキュリティ管理コストを避け、1ヶ月スケジュールに収める。メール/パスワード認証は次フェーズで検討 |

検討したがR1では不採用: Clerk(外部サービスに認証を丸投げしてUI部品も提供されるが、将来ユーザーが増えると月間アクティブユーザー数に応じて課金される。実装速度は最速)。
